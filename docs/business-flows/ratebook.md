# Business Flow: RateBook (ทำรายการสินเชื่อ)

Source: `image_figma/MainPage.png`, `image_figma/RateBookPage.png`

Entry point: Home (`/`) → "Ratebook" quick-action card → `/ratebook`. Also reached via `/customer-lead-list` → the arrow-icon link on an existing opportunity card, which lands on `/ratebook?opportunityId=<id>` for that row (no new row created), or → "จัดสินเชื่อ" (the focused lead), which navigates to `/ratebook?leadId=<id>` — the lead's info pre-fills the sidebar but no `customer_lead_opportunity` row is created yet; that only happens the first time "บันทึก Lead" is clicked (see [customer-lead-list.md](customer-lead-list.md)).

## Out of scope for this phase (flagged, not silently built)

- "บันทึก Lead" only persists to `customer_lead_opportunity` (step 8) — there's still no navigation/destination or success feedback after clicking it.
- The NCB เกรด is never auto-generated — `createCustomerLead` (`src/lib/actions/customer-lead.ts`) always saves `ncb_grade` as `null`, even after a Dipchip read, so a brand-new lead always shows the default "ตรวจ eNCB" button until checked on some page. Once checked anywhere, `customer_lead.ncb_grade` is the single source of truth and every page (this one, `/customer-lead-list`) reads that same value (step 3b/3c) rather than each opportunity's own stale snapshot. A real eNCB integration is out of scope.
- Reopening `/ratebook?opportunityId=…` seeds `showCarInfo` from the saved loan questions (`toCompleteLoanQuestions`), not only from a saved product — so an opportunity whose questions were answered but whose product was never chosen resumes with `CarInfoForm` already showing, instead of dropping back to the questions alone.
- `CarInfoForm`'s "สแกนเล่มทะเบียน" (scan registration book) button — visual only, no OCR/scanning integration.
- `CarInfoForm`'s dropdown option lists (brand, model, sub-model, year, condition, doors, car type, engine cc, transmission, body type) are mock data in `src/lib/mock.ts`, not sourced from any real vehicle database. The per-รุ่น `carTypeByDoors` / `transmissions` / `bodyTypes` data that now drives the derived ประเภทรถ, the narrowed จำนวนประตู list and the ระบบเกียร์/ประเภทตัวถัง auto-fill (steps 6d–6e) is hand-authored alongside it for all 55 models — it approximates the real Thai line-ups but is not sourced from a vehicle master, so a รุ่น shown as "one transmission only" is a mock fact, not a verified one. ยี่ห้อรถ → รุ่นรถ → รุ่นย่อย do cascade, and the catalog plus ประเภทรถ/ประเภทตัวถัง/ขนาดเครื่องยนต์ vary by the selected หลักประกัน type (มอเตอร์ไซค์/เก๋ง กระบะ ตู้/บรรทุก) — but ที่ดิน (land) has no dedicated **vehicle** catalog and still falls back to the เก๋ง กระบะ ตู้ one (`toVehicleCollateralType` in `src/lib/mock.ts`); a real land-specific field set (title deed type, area, location, etc.) is still out of scope. This no longer applies to the **product** catalog — land now has its own product set (see the `ProductCatalog` bullet below).
- `ProductGuide` (shown after "ดูราคาประเมิน") now computes its numbers from `getProductGuideData` (`src/lib/mock.ts`) using each vehicle model's mock `basePrice`, รุ่นปี ค.ศ.-based depreciation, and a สภาพรถ multiplier — but `basePrice` per model is still an approximate placeholder figure (not sourced from a real pricing feed/database), and รุ่นย่อย/ประเภทรถ/other fields still have no effect on the number. The component's props (`ProductGuideData`) remain shaped so a real pricing source can be swapped in later without changing the component.
- `ProductCatalog` (shown alongside `ProductGuide`) varies by หลักประกัน, ยี่ห้อรถ, and ราคาประเมิน (step 6f).
