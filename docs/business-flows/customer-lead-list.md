# Business Flow: Customer Lead List (ข้อมูลลูกค้า)

Source: `image_figma/CustomerLeadList.png`, `image_figma/CustomerInfomation/customer_info_start.png` (empty state), `image_figma/CustomerInfomation/customer_info_with_lead_list.png` (opportunity card)

Entry point: `/customer-form` → "ดำเนินการต่อ" (once enabled) → `/customer-lead-list?leadId=<id>` (see [customer-form.md](customer-form.md)). The `leadId` identifies the `customer_lead` row just created; the page lists only that customer's own `customer_lead_opportunity` rows (loan-application attempts) below it — each customer sees just their own list. Who counts as the same customer is decided by เบอร์มือถือ alone in `createCustomerLead` (see step 11 in [customer-form.md](customer-form.md)): the same phone always lands on the same list, a different phone starts a new one. Editing the phone later in `/ratebook` only changes that opportunity's snapshot — the opportunity stays on the list it was created under.

## Flow

| # | Trigger | Result | Notes |
|---|---------|--------|-------|
| 1 | `/customer-lead-list?leadId=<id>` page loads | Page title "ข้อมูลลูกค้า" renders a summary card for that lead, a tab row, and a "รายการ Lead" list below | `getCustomerLeadById` for the summary card (`src/lib/customer-lead.ts`), `listCustomerLeadOpportunitiesByLeadId` for the list (`src/lib/customer-lead-opportunity.ts`) — both are scoped to the same `customer_lead`; the list shows only `customer_lead_opportunity` rows whose `lead_id` is this lead |
| 2 | Summary card renders | Shows ชื่อ + นามสกุล, "บุคคลธรรมดา", a green "Dip Chip" badge (only when the lead has a เลขบัตรประชาชน — i.e. came from the card-read path, not manual key-in), masked เลขบัตรประชาชน, and formatted เบอร์มือถือ | Masking/formatting via `maskIdCardNumber` / `formatThaiPhone` (`src/lib/format.ts`) |
| 2b | Summary card's NCB slot renders | Shows a green "เกรด <grade>" badge if `customer_lead.ncb_grade` is already set, otherwise a "ตรวจ eNCB" button (disabled when there's no `leadId` in context) | `NcbCheckControl` (`src/components/organisms/NcbCheckControl.tsx`), reused from `/ratebook`'s `CustomerCollateralPanel` — see step 3c in [ratebook.md](ratebook.md) for the shared eNCB flow and mock values |
| 2c | Click "ตรวจ eNCB" | The same 5-step eNCB flow as `/ratebook`, opened on this page (`EncbCheckFlow`, step 3c in [ratebook.md](ratebook.md)): "กรุณาเสียบบัตรประชาชนผู้กู้" showing this lead's เลขบัตรประชาชน and name → click the gray card-reader box → "กำลังอ่านข้อมูลบัตร..." loading (2 s) → "ยินยอมการขอสินเชื่อและตรวจ eNCB" ("ยกเลิก" stops here with no grade) → "ยืนยันตัวตนด้วยใบหน้า" → "ถัดไป" → "กรอกรหัส OTP เพื่อยืนยันตัวตน" with fixed values where only "ยืนยัน" is clickable. After "ยืนยัน" the button is replaced by a green "เกรด A02" badge; the card also gains the "Dip Chip" badge and the masked เลขบัตรประชาชน, since the check reads the ID card | **Persists**: `updateCustomerLeadNcbGrade` (`src/lib/actions/customer-lead.ts`) writes the mocked grade onto this `customer_lead` row along with `verification_method = 'card'` and an ID number (the existing one if set, otherwise `mockKeyInCardCustomer.idCardNumber` — only a keyed-in lead lacks one), then revalidates `/customer-lead-list` so the page re-renders with it; it survives reload. `customer_lead.ncb_grade` is the single source of truth for NCB grade — `/ratebook` (both `?leadId=<id>` and `?opportunityId=<id>`) reads it fresh and displays it in preference to any `customer_lead_opportunity` row's own (possibly stale) snapshot column, so a grade checked here shows up there too without needing to re-check it, and `/ratebook`'s product catalog opens already filtered to that grade with "เลือก" instead of "ตรวจ eNCB" — see step 3b/3c in [ratebook.md](ratebook.md) |
| 3 | `/customer-lead-list` page loads with no `leadId` | Summary card renders with "-" placeholders instead of erroring; tab row shows only "รายการ Lead" | Direct navigation without a lead in context — with no lead there is no card read, so it follows the same rule as a manual-entry lead |
| 4 | Tab row renders | Shows all three tabs ("รายการ Lead", "รายการใบคำขอ", "รายการสัญญาสินเชื่อ") only when the focused lead came from the card-read path; otherwise just "รายการ Lead" | Gated on `customer_lead.verification_method === "card"` — the same signal that drives the "Dip Chip" badge. ใบคำขอ/สัญญา only ever follow a dipchip-verified customer, so hiding them keeps a manual-entry lead from advertising steps it can't reach |
| 5 | "รายการ Lead" tab (default active) | Lists this customer's `customer_lead_opportunity` rows (one per loan-application attempt), newest first, as a `CustomerLeadOpportunityCard` (`src/components/molecules/CustomerLeadOpportunityCard.tsx`) | Each card shows: a "ติดตาม" status badge, the opportunity's สาขา + เลขที่อ้างอิง ("branch_name • reference_code"), a blue "รีไฟแนนซ์" chip next to it whenever `refinance_status` is "ยังผ่อนอยู่" (nothing shown for "ผ่อนหมดแล้ว" or unanswered), the assigned staff name + code, a "สร้าง: <date>" chip, a row of collateral chips built from the opportunity's own columns — collateral-type label, `BRAND • MODEL`, ปี (with พ.ศ. in parens), สภาพรถ, and รุ่นย่อย, each omitted individually if its column is still unset (a single "-" chip shows when none are); ยอดขออนุมัติ (hardcoded `0.00`, see out-of-scope) and ยอดลูกค้าขอ (from `requested_amount`, defaulting to 0.00 if unset), and an arrow-icon link to `/ratebook?opportunityId=<id>`. The tab's copy still reads "รายการ Lead" even though it now lists opportunities, not leads — a deliberate non-change pending a separate copy decision |
| 6 | No opportunities exist yet | Empty state: `no_data.png` illustration + "ไม่มีรายการ" | Matches the empty state in the Figma reference (`image_figma/CustomerInfomation/customer_info_start.png`) |
| 7 | Click the arrow-icon button on a card | Navigates to `/ratebook?opportunityId=<id>` for that row's opportunity (no new row created — this just opens the existing draft) | See [ratebook.md](ratebook.md) |
| 8 | Click "จัดสินเชื่อ" (only when a `leadId` is in context) | Plain navigation to `/ratebook?leadId=<id>` — no `customer_lead_opportunity` row is created and nothing is written to the DB yet | Rendered as a disabled button when there's no `leadId`. `/ratebook` reads the lead (`getCustomerLeadById`) purely to pre-fill ข้อมูลลูกค้า/เลขบัตรประชาชน/NCB เกรด in the sidebar; the new draft still doesn't appear in "รายการ Lead" below until the user clicks "บันทึก Lead" there, which is what actually creates the opportunity row (snapshotting the lead's fields onto it) — see step 3a and step 8 in [ratebook.md](ratebook.md) |

## Out of scope for this phase (flagged, not silently built)
- "รายการใบคำขอ" and "รายการสัญญาสินเชื่อ" tabs — visual only even on the dipchip path; no application/contract data model exists yet, so only "รายการ Lead" has real content. They are also not clickable: the tab row is static markup, so "รายการ Lead" is always the active tab and there is no tab-switching behavior to hide.
- "ตรวจ eNCB" button on the summary card runs a mocked check (steps 2b–2c) — real eNCB, OTP and face-verification integrations are still out of scope. The grade it sets (`A02`) and the OTP screen's phone/code/ref are fixed in `mockEncbCheck` (`src/lib/mock.ts`), and the face step is a static photo.
- The เมนู (☰) icon in the header — visual only, no menu wired.
- "จัดสินเชื่อ" does not create a `customer_lead_opportunity` row itself (step 8) — it only navigates to `/ratebook?leadId=<id>` so the sidebar can pre-fill from the lead. The row is created lazily, the first time "บันทึก Lead" is clicked on `/ratebook` (see step 8 in [ratebook.md](ratebook.md)). `createOpportunityAndRedirect` (`src/lib/actions/customer-lead-opportunity.ts`) still exists but is currently unused by this page.
- The "รายการ Lead" tab label is unchanged even though its data source moved from `customer_lead` to `customer_lead_opportunity` — renaming it (e.g. to something like "รายการทำรายการสินเชื่อ") is a separate copy decision, not made here.
- Every `customer_lead_opportunity` card shows a "ติดตาม" status badge (`status` column) — this is the only status value that exists today; there's no follow-up workflow that transitions it to anything else yet.
- The card's branch (`branch_name`), เลขที่อ้างอิง (`reference_code`), and assigned staff (`staff_name` / `staff_code`) columns are real DB columns but hold **mocked** values stamped at creation time (`createCustomerLeadOpportunity` in `src/lib/actions/customer-lead-opportunity.ts`) — there's no branch or staff/auth entity in the app yet to source them from. `reference_code` is randomly generated per row (`CF` + 6 digits) so cards don't all show the same code; branch/staff reuse the same fixed mock values (`src/lib/mock.ts`) for every case.
- The card's ยอดขออนุมัติ is always hardcoded to `0.00` in the UI — there is no approval flow yet, so nothing populates a real approved amount. Only ยอดลูกค้าขอ reflects real data, from the opportunity's `requested_amount` — the วงเงินที่ขอ the user entered in `LoanCalBar` or `LeadLoanInfoCard`, falling back to the selected product's max approved amount only when neither was filled in (see step 6i/8 in [ratebook.md](ratebook.md)).
